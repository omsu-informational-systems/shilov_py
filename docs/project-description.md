# Проектный документ: Сервис торговой стратегии Momentum

## 1. Определение проекта
**Название сервиса:** momentum-strategy
**Назначение:** Автоматизированный сервис для принятия торговых решений на основе импульсной стратегии.
**Торговая идея:** Покупка активов, показывающих положительную динамику (рост) за определенный период, и продажа падающих активов. Стратегия предполагает, что текущий тренд сохранится в ближайшем будущем.
**Решаемая проблема:** Исключение человеческого фактора (эмоций) из трейдинга, автоматизация рутинного анализа графиков и оперативное реагирование на изменения рынка.
**Ожидаемый результат:** Работающий алгоритм, стабильно взаимодействующий с биржей и демонстрирующий доходность (или минимизацию убытков) на тестовом периоде.

## 2. Границы проекта
**Входит в сервис:** 
- Получение данных из Kafka.
- Вычисление индикатора Momentum.
- Формирование сигнала BUY/SELL/HOLD в Kafka.
- Отправка Heartbeat-сигналов
- Первичная регистрация сервиса на платформе преподавателя (связывание студента, стратегии и группы).
**Находится за пределами:**
- Реальное выставление заявок брокеру.
- Расчет прибыли/убытка (PnL) и ведение виртуального портфеля.
- Получение сырых данных с реальной биржи.
- Агрегация рекомендаций группы и расчет коллективного консенсуса.

**Внешние системы и пользователи:**
- **Преподавательская платформа:** Источник рыночных данных, координатор прогонов, потребитель торговых рекомендаций.
- **Инфраструктура передачи сообщений (Apache Kafka):** Промежуточный слой для асинхронного обмена событиями.
- **Разработчик / Администратор (Студент):** Пользователь, управляющий конфигурацией, развертыванием и жизненным циклом контейнера.

## 3. Взаимодействие с внешними системами
- **Преподавательская платформа (API):**
  - **Вход:** Топик с JSON-событиями о закрытии свечей (содержит тикер, close_price, sequenceNumber, runId).
  - *Выходные данные:* REST-запросы на создание ордеров (BUY/SELL).
  - *Аутентификация:* Bearer Token (API-ключ в заголовках).
- *Допущение:* Точный формат контракта платформы пока неизвестен, ожидается REST API + JSON.

## 4. Состав решения (Компоненты)
- **Серверное приложение (FastAPI):** Ядро логики, принимает решения.
- **База данных (PostgreSQL):** Хранение истории сделок, конфигурации алгоритма и логов работы.
- **Брокер сообщений (RabbitMQ / Redis - опционально в будущем):** Асинхронная обработка потока котировок, если потребуется масштабирование.

## 5. Роли
- **Разработчик:** Пишет код, настраивает алгоритм, развивает сервис.
- **Оператор/Владелец:** Запускает контейнер, мониторит работу через логи, пополняет баланс на платформе.
- **Владелец внешней системы (Преподаватель):** Предоставляет API биржи.
*(Остальные роли, такие как заказчик, избыточны для студенческого проекта).*

## 6. Обоснование выбора инструментов
- **Язык программирования — Python 3:**
  - Обеспечивает минимальный объем инфраструктурного шаблонного кода (boilerplate) по сравнению с Java/C#, позволяя сфокусироваться на предметной области (DDD) и контрактах сообщений.
  - Нативная поддержка асинхронного ввода-вывода через `asyncio`, что необходимо для одновременного обслуживания фонового цикла чтения Kafka и ответов на HTTP-запросы мониторинга в рамках одного процесса.
  - Наличие зрелых асинхронных драйверов для брокеров сообщений (`aiokafka`) и баз данных (`asyncpg`).
- **Веб-каркас — FastAPI:**
  - Легковесный ASGI-фреймворк с минимальным оверхедом по памяти.
  - Встроенный механизм `lifespan` для корректного управления жизненным циклом фоновых задач (graceful shutdown подключений к Kafka и пулу БД при получении сигналов SIGTERM).
  - Автоматическая валидация структур данных через Pydantic.
- **База данных — PostgreSQL:**
  - Поддержка транзакций (ACID) для атомарной фиксации обработанного `sequenceNumber` и обновленной цены актива, что исключает состояние гонки при рестарте сервиса.
- **Контейнеризация — Docker:**
  - Фиксация версии системных зависимостей, интерпретатора и библиотек, обеспечивающая гарантированную воспроизводимость запуска без локальной настройки окружения.
- **Управление зависимостями — Poetry:**
  - Детерминированная фиксация дерева зависимостей через `poetry.lock`, предотвращающая конфликты версий при сборке в CI/CD и Docker.
- **Система контроля версий — Git + GitHub:**
  - Совместное версионирование документации и исходного кода в едином репозитории, отслеживание изменений проектных решений через историю коммитов.
